# How to Adopt Nebuko

Nebuko runs a multi-agent workflow on **your** issues and pull requests:
plan → context → implement → review, with human approval gates, driven entirely
from issue comments. This page takes a repository from zero to a first run.

For the underlying concepts first, read [architecture.md](./architecture.md)
and [workflows.md](./workflows.md).

---

## 1. What you get

Adding Nebuko to a repository gives you:

- **Orchestration on your own issues and PRs** — start a workflow
  (`/nebuko run workflow --name default`), or mention an agent directly
  (`@@architect`, `@@context`, `@@dev`, `@@review`) from an issue body or comment.
- **Nebuko branding in the thread** — every orchestrator comment is prefixed
  with the theme-adaptive Nebuko logo mark (a `<picture>` block serving
  `mark-light.svg` / `mark-dark.svg`), exactly as on this project's own issues.
- **Branded commit author** — commits and PR branches created by the
  implementation step are authored as
  `nebuko <nebuko@users.noreply.github.com>`.
- **AI-attribution signature** — agent answers end with a short
  "generated by an AI agent … on behalf of &lt;user&gt;" line. This line is
  emitted by the agent prompt (best-effort), not enforced by the engine.
- **Coming — `nebuko[bot]`** — a GitHub App identity that makes Nebuko a
  first-class actor (its own avatar, `nebuko[bot]` actor name, and automatic
  logo). **Not available yet**; tracked separately.

> Today Nebuko runs in **PAT mode** (alpha default): it acts through a
> fine-grained `GH_PAT` that you own.

## 2. Prerequisites

1. **A caller repository on GitHub.** Nebuko's reusable workflow is hosted in
   the public `nebuko/nebuko` repository — GitHub requires the *called*
   repository to be public for a reusable workflow to be used from another
   repository. Your own (caller) repository can be public or private.
2. **A runner.** GitHub-hosted `ubuntu-latest` by default; you can point the
   jobs at your own runners instead (section 6).
3. **A fine-grained `GH_PAT`** scoped to the account that owns the target
   repositories. Minimum repository permissions:
   - **Contents:** read and write — clone and push branches.
   - **Pull requests:** read and write — open and update PRs.
   - **Issues:** read and write — read triggers, post comments, persist state.
4. **A provider API key** — one of `OPENROUTER_API_KEY`,
   `COMMANDCODE_API_KEY`, or `LOCAL_VLLM_API_TOKEN`, matching the provider you
   configure (section 5).

## 3. The entrypoint (copy-paste)

Create `.github/workflows/nebuko.yaml` in your repository and commit this file
as-is:

```yaml
name: Nebuko

on:
  issues:
    types: [opened, edited, assigned, closed]
  issue_comment:
    types: [created]

permissions:
  contents: write
  pull-requests: write
  issues: write

jobs:
  agent:
    uses: nebuko/nebuko/.github/workflows/nebuko-workflow.yaml@main
    with:
      agent_config_path: "agent-config.yaml"
    secrets:
      OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
      GH_PAT: ${{ secrets.GH_PAT }}
```

`OPENROUTER_API_KEY` and `GH_PAT` are repository secrets, added under
**Settings → Secrets and variables → Actions**.

### Inputs

Every input is optional; defaults are shown. Pass them under `with:`.

| Input | Type | Default | Purpose |
|-------|------|---------|---------|
| `agent_config_path` | string | `agent-config.yaml` | Path to your layered config (section 5). |
| `runs_on` | string | `ubuntu-latest` | Runner label used by the jobs (section 6). |
| `circuit_breaker_threshold` | number | `25` | Bot-marker count that trips the circuit breaker (per-issue override: `/nebuko update circuit-breaker --value <n>`). |
| `pin_comment` | boolean | `false` | Pin every agent-step comment for verbatim context injection. |
| `history_comment_count` | number | `5` | Most recent comments injected into each agent call. |
| `python_version` | string | `3.13` | Python version installed on the runner. |
| `enable_uv_cache` | boolean | `true` | Enable the `uv` dependency cache. |
| `prompt_body` | string | `""` | Prompt/body text for programmatic (`workflow_call`) callers. |
| `checkout_ref` | string | `""` | Explicit ref (SHA, tag, or branch) for the workspace checkout. When empty, the checkout follows the workflow's own commit if the workflow is checking out its own repo (issue #862), else the event default. |
| `CALLER_AUTH` | string | `on` | When `on` (default), only OWNER/MEMBER/COLLABORATOR authors may trigger from issues/comments; set to `off` to allow anyone. |
| `EXTRA_SECRET_1_NAME` … `EXTRA_SECRET_9_NAME` | string | `""` | Env var name materialized from the matching `EXTRA_SECRET_n_VALUE` secret — use for MCP tokens (section 3.1). |

### Secrets

| Secret | Required | Purpose |
|--------|----------|---------|
| `GH_PAT` | **yes** | Fine-grained PAT for git push, issue/PR API calls, and comments. |
| `OPENROUTER_API_KEY` | optional | Provider key, used as the fallback LLM key. |
| `COMMANDCODE_API_KEY` | optional | CommandCode subscription provider. |
| `LOCAL_VLLM_API_TOKEN` | optional | Local vLLM provider. |
| `BRAVE_API_KEY` | optional | Brave Search MCP token (the named alias of the slot pattern in section 3.1). |
| `EXTRA_SECRET_1_VALUE` … `EXTRA_SECRET_9_VALUE` | optional | Values materialized into the env vars named by the `EXTRA_SECRET_n_NAME` inputs (section 3.1). |

At least one provider secret must be wired for the agents to reach an LLM.

### 3.1 Wiring extra secrets (MCP tokens)

MCP servers need their own private tokens. You can hand the engine **any** such
token without editing the reusable workflow: add a repository secret, then point
one of nine generic slots at the env var name the MCP expects. The `with:` input
carries the *name*, the `secrets:` block carries the *value*:

```yaml
jobs:
  agent:
    uses: nebuko/nebuko/.github/workflows/nebuko-workflow.yaml@main
    with:
      agent_config_path: "agent-config.yaml"
      EXTRA_SECRET_1_NAME: "BRAVE_API_KEY"       # env var the MCP reads
    secrets:
      OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
      EXTRA_SECRET_1_VALUE: ${{ secrets.BRAVE_API_KEY }}
      GH_PAT: ${{ secrets.GH_PAT }}
```

- Slot `n` pairs `EXTRA_SECRET_n_NAME` with `EXTRA_SECRET_n_VALUE`; indices run
  `1`–`9`.
- Empty slots are ignored; on a duplicate name the lowest populated slot wins.
- Names reserved for the runner (`GITHUB_*`, `ACTIONS_*`, `RUNNER_*`, `PATH`,
  `HOME`, `GITHUB_TOKEN`, `GH_TOKEN`) are dropped, so a slot cannot clobber
  engine internals.
- Precedence: a slot value (written to `$GITHUB_ENV`) overrides a same-named
  job-level alias such as the named `BRAVE_API_KEY`; a name the engine step
  binds explicitly (`LOCAL_VLLM_API_TOKEN`) shadows `$GITHUB_ENV`, so mapping a
  slot onto it has no effect.

Adding an MCP token is therefore a repository secret plus two lines in *your*
entrypoint — never an edit to `nebuko-workflow.yaml`. See
[ADR-0008](./adr/0008-mcp-secret-env-injection.md) for the rationale.

## 4. Authentication — PAT mode (alpha default)

In PAT mode Nebuko acts entirely through the `GH_PAT` you supply: it clones,
pushes branches, opens/updates PRs, and posts comments as the token's owner.
The token is passed to the reusable workflow as a secret and is never written
to the checkout.

**What the token must be able to do**

- Push branches and read contents in the target repository.
- Read and write issues, comments, and pull requests.

**Security notes**

- Use a **fine-grained** token, not a classic one. A fine-grained PAT is limited
  to a single user or organization and can be narrowed to specific repositories.
- Set an **expiration**; rotate before it lapses. GitHub removes tokens unused
  for a year.
- Organization owners can require **approval** for fine-grained tokens that can
  access org resources — expect an approval step on org repositories.
- Prefer passing the narrowest token that covers the repositories you point
  Nebuko at. The optional GitHub App upgrade (section 8) replaces the PAT with
  short-lived, per-repository tokens.

**Branding you get in PAT mode** — the logo-mark comment prefix, the branded
`nebuko` commit author, and the prompt-emitted AI-attribution line (section 1).
The `nebuko[bot]` actor requires the GitHub App and is not available yet.

## 5. Provider configuration — ready-to-paste configs

Commit an `agent-config.yaml`. Nebuko resolves it — and every other config
artifact — through a layered lookup: a repo override under `.nebuko/` first,
then the copy shipped in `defaults/`. Add yours at
`.nebuko/agents/agent-config.yaml` (or set `agent_config_path` to wherever you
keep it). The file is layered **providers → llms → agents**; the full schema is
in [configuration.md](./configuration.md). The shipped `defaults/agents/` and
`defaults/prompts/` work with no local files at all, so the config below is the
whole minimal setup.

### OpenRouter

`agent-config.yaml`:

```yaml
providers:
  openrouter:
    api_url: "https://openrouter.ai/api/v1"
    api_token_env: "OPENROUTER_API_KEY"

llms:
  my-model:
    model_path: "openrouter/deepseek/deepseek-chat-v3-0324"
    provider: "${providers.openrouter}"
    default_temperature: 0.7

agents:
  architect:
    model: "${llms.my-model}"
    prompt_file: "defaults/prompts/architect.md"
    tools: ["think", "finish"]

  dev:
    model: "${llms.my-model}"
    prompt_file: "defaults/prompts/dev.md"
    tools: ["terminal", "file_editor", "task_tracker", "think", "finish"]

  review:
    model: "${llms.my-model}"
    prompt_file: "defaults/prompts/review.md"
    tools: ["think", "finish"]
```

Wire the matching secret in your entrypoint (section 3):

```yaml
    secrets:
      OPENROUTER_API_KEY: ${{ secrets.OPENROUTER_API_KEY }}
      GH_PAT: ${{ secrets.GH_PAT }}
```

> `prompt_file` matters for its **file name** only: Nebuko resolves each agent's
> prompt through the same layered lookup (`.nebuko/prompts/` override → shipped
> `defaults/prompts/`), so the shipped prompt is used unless you add an override
> with that name.

### Local vLLM

For a self-hosted vLLM endpoint, inline the URL and point `api_token_env` at
the token secret:

```yaml
providers:
  local_vllm:
    api_url: "http://192.168.1.64:31728/v1"
    api_token_env: "LOCAL_VLLM_API_TOKEN"

llms:
  qwen:
    model_path: "hosted_vllm/qwen-3-6-27b"
    provider: "${providers.local_vllm}"
    default_temperature: 0.7

agents:
  architect:
    model: "${llms.qwen}"
    prompt_file: "defaults/prompts/architect.md"
    tools: ["think", "finish"]
```

Wire the `LOCAL_VLLM_API_TOKEN` secret in your entrypoint:

```yaml
    secrets:
      LOCAL_VLLM_API_TOKEN: ${{ secrets.LOCAL_VLLM_API_TOKEN }}
      GH_PAT: ${{ secrets.GH_PAT }}
```

`api_url` may also be the **name** of an environment variable holding the URL
(resolved at config-load time, mirroring `api_token_env`) — e.g.
`api_url: "LOCAL_VLLM_API_URL"`. That form only helps when the variable is
actually present on the runner, so inline the URL unless your runner sets it.

> **CommandCode / subscription providers.** See
> [subscription-plans.md](./subscription-plans.md) for the provider stanza and
> a working `agent-config-commandcode.yaml` example.

## 6. Choosing `runs_on`

The workflow runs on GitHub-hosted runners by default. Select a runner with the
`runs_on` input:

```yaml
    with:
      runs_on: "ubuntu-latest"        # default — GitHub-hosted
      # runs_on: "self-hosted"        # your own runner
      # runs_on: "[self-hosted, linux, x64]"   # label combination
```

- **GitHub-hosted (`ubuntu-latest`)** — nothing to install; the workflow sets up
  Python and `uv` itself. Billed by GitHub per the repository's plan.
- **Self-hosted** — use the default `self-hosted` label or a combination such as
  `[self-hosted, linux, x64]` (see GitHub's
  [runner labels](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/using-self-hosted-runners-in-a-workflow)).
  Runners are **consumer-managed**: you own their availability, patching, and
  network access to any private vLLM endpoint.

## 7. Pinning and upgrades

The entrypoint above pins `@main`. Release tags (starting `0.1.0`) will be
published before public launch; once they exist, pin the release tag for
reproducibility, or a full commit SHA for the strongest guarantee:

```yaml
    uses: nebuko/nebuko/.github/workflows/nebuko-workflow.yaml@0.1.0
    # or: .../nebuko-workflow.yaml@<full-commit-sha>
```

GitHub Actions does **not** follow redirects for reusable workflows: if the
called repository or workflow path is ever renamed, callers pinned to the old
name fail. Pinning to an immutable ref is what keeps an upgrade deliberate.

## 8. Optional GitHub App (coming)

A future upgrade replaces the PAT with a GitHub App installation:

- short-lived, per-repository installation tokens instead of a long-lived PAT;
- the `nebuko[bot]` actor identity (GitHub's `<app-name>[bot]` convention);
- an automatic Nebuko logo on the App's comments, without the `<picture>` prefix.

This is **not available yet** and is tracked separately. Until it lands, PAT
mode (section 4) is the supported path.
